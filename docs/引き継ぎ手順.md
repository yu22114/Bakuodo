# 引き継ぎ手順（実装担当用）

運営メンバーに開発を渡すときに、自分がやることの全部。上から順にやれば終わる。
所要 合計90分くらい。以降は月1で10分。

各手順に「なぜやるか」を書いた。理由が納得できないものは飛ばしていい。

---

## Phase 0 — 渡す前の保険（30分・ここだけは飛ばさない）

### 0-1. コードの復元ポイントを作る

```bash
git tag handover-2026-08-14 && git push origin handover-2026-08-14
```

```bash
git branch backup/2026-08-14 && git push origin backup/2026-08-14
```

> **なぜ:** タグとブランチが両方GitHubにあれば、`main` を吹き飛ばされても戻せる。
> GitHubがFreeプランのprivateリポジトリなので**ブランチ保護が使えない**（技術的には
> 誰でも `main` にpushできる）。その代わりの保険がこれ。

### 0-2. 自分用のアーカイブを取る

```bash
git clone --mirror https://github.com/yu22114/Bakuodo.git ~/archive/bakuodori-2026-08-14.git
```

> **なぜ:** いつか名義を移すとリポジトリが自分のアカウントから消える。履歴つきの完全コピーを
> 手元に持っておけば、後から作った証明にも、ポートフォリオの材料にも使える。

### 0-3. DBのバックアップを取る（2本セット）

接続文字列は Supabase → Project Settings → Database → Connection string からコピー。

```bash
npx supabase db dump --db-url "接続文字列" -f ~/archive/bakuodori-schema-2026-08-14.sql
```

```bash
npx supabase db dump --db-url "接続文字列" --data-only -f ~/archive/bakuodori-data-2026-08-14.sql
```

> **なぜ2本:** `db dump` は初期設定だと**入れ物の形しか保存しない**。中身は `--data-only` で
> 別に取る必要がある。片方だけだと復元できない。
>
> **なぜ今:** Supabase無料プランには自動バックアップが無い。ここで取ったものが唯一の原本。

### 0-4. 名前を残す（任意）

READMEかCREDITS.mdに、自分の担当範囲を書いてコミットしておく。

> **なぜ今:** 鍵を持っている今なら誰の許可も要らない。渡した後に頼む話ではない。
> なお `git shortlog -sn` の履歴は移管しても消えないので、最低ラインの証拠は既にある。

## Phase 1 — 招待（15分）

> **方針（2026-08-18）:** 権限は絞らない。最終的にこのサービスは彼らのものになるし、
> 壊れてもClaudeを使って直せる。**絞ることで自分に問い合わせが戻ってくるほうが損。**
> ただし Phase 0 のバックアップだけは、渡す前に必ず取っておく（データだけは戻らないため）。

### 1-1. GitHub：**Write** で招待

Settings → Collaborators → Add people

> **なぜAdminではなくWriteか:** ここだけは絞る。Adminはリポジトリごと削除できて、
> それをやられると `git revert` も過去の履歴も一緒に消える＝復旧手段が無くなる。
> Writeでもコードは自由に変えられるので、開発には何も困らない。
> 名義ごと渡す日（Phase 5）にAdminへ上げる。

### 1-2. Supabase：**Administrator** で招待

Organization → Team → Invite

> **なぜ招待するのか:** DBを変える作業（手順書 第4章のSQL実行）を自分たちでやってもらうため。
> ここを閉じると機能追加のたびに自分に戻ってくる。それを避けるのが今回の目的。
>
> **なぜ弱い権限にこだわらないか:** 無料プランには Read-Only ロールが無く、いちばん弱い
> Developer でも SQL Editor が使える＝結局なんでも実行できる。絞ったつもりになるだけなので、
> それなら普通に渡して「足し算だけ」のルールを守ってもらうほうが誠実。
>
> **Ownerだけは渡さない**（請求とプロジェクト削除）。これも Phase 5 で渡す。

### 1-3. Vercel：**招待しない**

> **なぜ:** Hobbyプランはメンバー招待ができない（共同作業はProから）。そして必要もない。
> 本番を戻す作業は `git revert` でGitHubだけで完結する（手順書 第5章）。
>
> **2026-08-18追記:** Preview URLでの確認をやめたので、Vercelを見る用事がさらに減った。
> （Preview URLは Vercel Authentication が有効でログインしないと開けない状態のままだが、
> 使わないので放置でいい）

### 1-4. 環境変数を渡す：**不要になった**

> **なぜ不要か:** 全員ブラウザ版のClaude Codeで作業する＝自分のパソコンでアプリを動かさない。
> 動かさないなら `.env.local` も要らない。本番のビルドはVercelが自分の設定値でやる。
>
> どうしても手元で動かしたい人が出てきたら、その人にだけ
> `NEXT_PUBLIC_SUPABASE_URL` と `NEXT_PUBLIC_SUPABASE_ANON_KEY` を渡す。
> この2つは元々ブラウザに載る公開値なので渡してよい。
>
> **絶対に渡さないもの:** `SUPABASE_SERVICE_ROLE_KEY`。これはRLSを全部無視できる
> マスターキーで、Vercelの設定画面の中だけに存在する（`app/api/remind/route.ts` が使っている）。

## Phase 2 — 動作確認（10分・自分の手で1回やる）

1. `main` に revert を1回試して、本番が戻ることを確認する
   > **なぜ:** Preview確認をやめた今、**これが唯一の安全網**。
   > 「壊れたらこれで戻す」と教える手順を、自分が一度も試していないのは危ない。

2. 開催リマインドの通知が届くか確認する（`/api/remind` が毎朝9時JSTに動く）
   > **なぜ:** 唯一、人の操作なしに勝手に動く仕組み。壊れていても誰も気づけない。
   > 通知が二重に来ていないかも一緒に見る。

3. 自分のスマホで本番を一周する（サイファー・レッスン・スポット・プロフィール）
   > **なぜ:** 彼らの確認手段が「本番を見る」だけになったので、
   > その手段が成立することを自分で一度なぞっておく。

## Phase 3 — 説明（30分・口で伝える）

`docs/はじめかた.md` を渡して、以下4つだけ口で補足する。残りは読めばわかる。

1. **出したら本番。プレビューは無い**＋ **DBは1冊しかない**
2. **DBは足し算だけ。引き算はしない**（消さなければデータは死なない）
3. **壊れたらClaudeに「さっきのマージを取り消して」と言う**（`git revert`）
4. **SQLを実行したら Security Advisor を見る**（RLS忘れは漏洩で、バックアップでは直らない）

> **なぜこの4つか:** 残りの事故は全部リカバリできる。この4つだけがリカバリ不能か、
> 自分が呼ばれる原因になる。

## Phase 4 — 渡した後の自分（月10分）

**やること**

- 月1で Phase 0-3 のDBダンプを取る（日付を変えるだけ）

**見るだけ（介入しない）**

- Supabase → Advisors に警告が溜まっていないか
- 各サービスの請求（Hobby/Freeのままなら上限で止まるので、金が溶けることはない）

**自分が呼ばれてよい条件＝はっきり伝えておく線**

- 決済 / 外部サービス連携 / メール送信 / `SERVICE_ROLE_KEY` を触る話
- 有料プランに上げる話

> **なぜ線を引くか:** 「足し算だけ」ルールで守れる範囲がここまで。これを超える機能は
> 設計判断が必要で、Claudeに丸投げすると鍵の扱いを間違える。
> そしてこの規模になった時が、**金と名義を移すタイミング**。

## Phase 5 — 名義を渡す日（そうなったら）

移し忘れると後で必ず連絡が来るもの一覧。

| 移すもの | 場所 |
|---|---|
| GitHubリポジトリ | Settings → Transfer ownership |
| Vercelプロジェクト | Project Settings → Transfer（環境変数は再設定が必要） |
| Supabaseプロジェクト | 相手のOrganizationへ移譲 |
| **Google OAuthのクライアント** | Google Cloud Console。渡し忘れるとログインが将来直せなくなる |
| **支払い方法** | 各サービスのカード登録。自分のカードのまま払い続ける事故が一番多い |
| ドメイン（あれば） | レジストラの移管 |
| Vercelの cron `/api/remind` の存在 | `vercel.json` に定義。毎朝9時（JST）に開催リマインドを作ると伝える |

そして **「◯月◯日以降は対応しません」を文字で残す。** 口約束だと必ず連絡が来る。
